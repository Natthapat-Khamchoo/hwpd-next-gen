### 1.1 เพิ่มคอลัมน์ใหม่ใน schema.py ครบทุกข้อในรอบเดียว

**ทำไมทำก่อน:** โค้ดอ้างคอลัมน์ด้วยตำแหน่ง ไม่ใช่ชื่อ ถ้าทยอยเพิ่มทีละวันจะต้องแก้

**ทุกคอลัมน์ต่อท้ายเท่านั้น** ไม่มีการแทรกกลาง

**ทำ:**

| ตาราง | คอลัมน์ที่เพิ่ม | requirement |
|---|---|---|
| `tb_Checkpoints` | ละติจูด, ลองจิจูด | ข้อ 16 |
| `tb_FuelOil` | Slip_Attachment_Folder | ข้อ 7 |
| `tb_DailyResult` | จับกุมตามหมายจับ (ราย), จับกุมซึ่งหน้า (ราย) | ข้อ 15 |

แก้ `prepare_*` ใน `report_service.py` ให้ส่งค่าครบตามช่องใหม่ เพิ่มพารามิเตอร์
`extra_officers` ให้ `prepare_daily_report` และ `folder_url` ให้ `prepare_fuel_record`
พร้อมต่อสายใน `main.py` ให้ฟอร์มน้ำมันส่งโฟลเดอร์ไฟล์แนบเข้ามา

**ผล:** 296 passed (เดิม 284) เพิ่มเทสใหม่ 12 ตัวใน `tests/test_report_extra_fields.py`
ที่ตรวจว่าค่าลง **ถูกช่อง** ไม่ใช่แค่จำนวนช่องตรง

**ปัญหาที่เจอระหว่างทาง (แก้แล้ว 3 เรื่อง):**

1. `test_national.py` เดิมอ่าน JSON สาเหตุอุบัติเหตุด้วย `built[-1]` พอเพิ่มคอลัมน์
   ต่อท้าย ตำแหน่ง `-1` กลายเป็นคอลัมน์ใหม่ เทสจึงพัง **ซึ่งเป็นเรื่องดี** เพราะแปลว่า
   เทสจับการเลื่อนคอลัมน์ได้จริง แก้เป็น `built[-2]` แล้วเพิ่มเทสใหม่ตรวจ flag archive
2. เขียน f-string ซ้อน quote เดียวกัน (`f"...{f' ({o['role']})'}..."`) ซึ่งใช้ได้เฉพาะ
   Python 3.12 ขึ้นไป แต่ **Render ตั้ง `PYTHON_VERSION: 3.11.9`** เครื่อง dev เป็น 3.13
   จึงไม่ฟ้อง แต่จะพังตอน deploy เปลี่ยนไปใช้ `.format()` แทน
3. `ensure_worksheet` เขียนหัวคอลัมน์ให้เฉพาะแท็บที่สร้างใหม่ แท็บเดิมที่ใช้งานอยู่จะ
   ยังถือหัวตารางชุดเก่า ข้อมูลใหม่จะลงในช่องที่ไม่มีป้ายกำกับ (โค้ดอ่านถูกเพราะอ้าง
   ตำแหน่ง แต่คนเปิดชีตดูจะงง) จึงเขียน `scripts/sync_sheet_headers.py` เพิ่ม

**`scripts/sync_sheet_headers.py`** แตะเฉพาะแถวที่ 1 ไม่แตะข้อมูล และ**ปฏิเสธที่จะทำงาน**
ถ้าหัวตารางเดิมยาวกว่า schema หรือไม่ใช่คำนำหน้าของหัวใหม่ ซึ่งแปลว่ามีคนแทรกคอลัมน์
กลางตารางเอง กรณีนั้นต้องให้คนดูก่อน แก้อัตโนมัติแล้วข้อมูลจะย้ายผิดช่องทั้งตาราง

**[ค้าง] ยังไม่ได้รันกับชีตจริง** ต้องรัน `python scripts/sync_sheet_headers.py --dry-run`
ก่อนใช้งานจริง ตอนนี้ทดสอบได้แค่ระดับ import เพราะไม่มี credentials ในเครื่องนี้

### 1.2 audit_service + tb_AuditLog

**ทำ:** สร้าง `app/services/audit_service.py` เก็บร่องรอยว่าใครทำอะไรกับรายการไหน
ต่อสายเข้า `/api/records/approve` และ `/api/records/cancel` แล้ว

**การตัดสินใจสำคัญ 3 ข้อ พร้อมเหตุผล:**

1. **บัฟเฟอร์ระหว่าง request แล้วเขียนทีเดียวตอนจบ ไม่เขียนทันทีที่เรียก** ระบบใช้
   บัญชี Google บัญชีเดียวทั้งระบบและชนโควตา 60 คำขอ/นาที มาแล้ว การเขียน audit
   ทุกครั้งที่มี action จะเพิ่มจำนวนคำขอเป็นเท่าตัว หนึ่ง request ที่แตะ 3 รายการ
   ตอนนี้กิน 1 คำขอ ไม่ใช่ 3 (มีเทสยืนยัน)
2. **เขียนเฉพาะเมื่อ response เป็น 2xx** ผ่าน middleware ใน `main.py` audit ของ
   action ที่ถูกปฏิเสธ (403/400/502) คือร่องรอยของสิ่งที่ไม่เคยเกิดขึ้น ถ้าเก็บไว้
   ตอนสอบย้อนหลังจะแยกไม่ออกว่ารายการไหนสำเร็จจริง
3. **เขียน audit ไม่สำเร็จต้องไม่ทำให้ action ของผู้ใช้ล้มตาม** ตอนที่ flush
   รายการหลักถูกบันทึกไปแล้ว ถ้าขว้าง error ตรงนั้นผู้ใช้จะเห็นว่าล้มเหลวทั้งที่ข้อมูล
   เข้าไปแล้ว แล้วกดซ้ำจนได้ข้อมูลซ้ำ จึงบันทึกเป็น log ระดับ error พร้อมเนื้อรายการ
   ที่เขียนไม่สำเร็จ ให้ตามเก็บย้อนหลังได้จาก log เซิร์ฟเวอร์

**เพิ่ม `sheets_service.append_report_rows()`** สำหรับเขียนหลายแถวด้วยคำขอเดียว
ของเดิมมีแต่ `append_report_row` ทีละแถว

**ผล:** 311 passed (เดิม 296) เพิ่มเทส 15 ตัวใน `tests/test_audit_service.py`

**ปัญหาที่ต้องระวังและพิสูจน์แล้วว่าไม่เกิด:** บัฟเฟอร์ผูกกับ `ContextVar` แต่ endpoint
แบบ `def` (ไม่ใช่ `async def`) ของ FastAPI ทำงานใน threadpool คนละที่กับ middleware
ที่เปิดบัฟเฟอร์ไว้ **ถ้า context ไม่ข้ามไป audit จะหายเงียบโดยไม่มี error ให้เห็นเลย**
ซึ่งเป็นอาการที่จะไม่มีใครรู้ตัวจนถึงวันที่ต้องใช้ log จริง จึงเขียนเทส
`TestBufferSurvivesTheMiddlewareBoundary` ยิงผ่าน HTTP จริงด้วย `TestClient` พิสูจน์
ทั้งเคสสำเร็จ (เขียน) และเคส 403 (ไม่เขียน) ผ่านทั้งคู่

### 1.3 useFormDraft — คงค่าฟอร์มเมื่อย้อนกลับ (ข้อ 12 เสร็จ)

**ทำ:** `src/hooks/useFormDraft.ts` + `src/components/forms/DraftNotice.tsx`
ต่อเข้าฟอร์มครบ **11 ร่าง ใน 9 ฟอร์ม**

| ฟอร์ม | คีย์ร่าง |
|---|---|
| รายงานประจำวัน (5 แท็บ) | `daily.t1`, `daily.t2` + `daily.t2.charges`, `daily.t3`, `daily.t5` + `daily.t5.officers` |
| ตั้งด่าน | `checkpoint` |
| จับกุม | `arrest` + `arrest.team` / `.charges` / `.suspects` / `.seized` |
| อุบัติเหตุ | `accident` |
| แจ้งภารกิจ | `mission` + `mission.units` |
| บันทึกข้อความ | `document` |
| รับเสด็จ | `royal_guard` + `royal_guard.cmd` |
| น้ำมัน (2 แท็บ) | `fuel.refuel`, `fuel.oil` |
| เครื่องมือ (จับกุมอัตโนมัติ) | `tools.auto_arrest` + `.suspects` |

**การตัดสินใจ:**

- **`sessionStorage` ไม่ใช่ `localStorage`** ร่างที่ยังไม่ส่งเป็นของรอบการทำงานนั้น
  ปิดเบราว์เซอร์แล้วควรจบ ไม่ใช่ค้างข้ามวันจนเจ้าหน้าที่เผลอส่งข้อมูลของเมื่อวาน
- **คีย์แยกตาม username** เครื่องในหน่วยใช้ร่วมกันหลายคน ร่างของคนก่อนหน้าต้องไม่โผล่
  มาให้คนที่ล็อกอินต่อ
- **มีแถบแจ้งเตือนพร้อมปุ่มล้าง** การกู้ค่าอัตโนมัติแบบเงียบ ๆ อันตรายกว่าข้อมูลหาย
  เพราะคนที่ตั้งใจกรอกใบใหม่จะเผลอส่งค่าของใบก่อนไปโดยไม่ทันสังเกต
- **แต่ละแท็บเก็บร่างแยกกัน** ฟอร์มประจำวันมี 5 แท็บที่กรอกคนละเรื่อง กดล้างที่แท็บหนึ่ง
  ต้องไม่ลบของอีกแท็บ

**ปัญหาที่เจอและแก้:**

1. **ร่างเปล่าค้างหลังบันทึกสำเร็จ** ฟอร์มรีเซ็ตตัวเองหลัง submit ทำให้ effect เขียน
   ร่างของฟอร์มเปล่าลงไปใหม่ รอบหน้าจึงขึ้น "กู้ร่างคืนแล้ว" ทั้งที่ไม่มีอะไรกู้
   แก้ด้วยการข้ามการเขียนเมื่อค่าปัจจุบันเท่ากับค่าตั้งต้น
2. **การ merge ร่างทับค่าตั้งต้นทำ array พัง** ฟอร์มจับกุมเก็บรายชื่อชุดจับกุม
   ผู้ต้องหา ของกลาง เป็น array การ `{...initial, ...saved}` กับ array ได้ object
   ที่มีคีย์เป็นตัวเลข ซึ่งทำให้ `.map()` พังทั้งฟอร์ม แก้ด้วยการใช้ค่าที่บันทึกไว้ตรง ๆ
   เมื่อฝั่งใดฝั่งหนึ่งเป็น array
3. **ธงกันเขียนซ้ำหลังล้างทำให้ร่างใหม่ไม่ถูกเก็บ** ตอนแรกตั้งธงถาวรว่า "ล้างแล้ว"
   เพื่อกันไม่ให้ debounce ที่ค้างเขียนกลับ แต่ธงนั้นทำให้การกรอกครั้งถัดไปในฟอร์ม
   ที่ยังไม่ unmount (เช่น สลับแท็บ) ไม่ถูกเก็บเลย เปลี่ยนเป็นแค่ยกเลิก timer ที่ค้าง

**ทดสอบ:** `tsc -b` และ `oxlint` เขียว ไม่มี warning ใหม่ และ**ทดสอบผ่านเบราว์เซอร์จริง
ด้วย Claude in Chrome** สี่เคส

| เคสที่ทดสอบ | ผล |
|---|---|
| กรอกฟอร์มด่าน กดกลับ เข้าใหม่ | ค่าคืนครบ ขึ้นแถบแจ้งเตือน |
| กดปุ่ม "ล้างแล้วเริ่มใหม่" | ร่างหายจาก sessionStorage ช่องว่าง แถบหาย |

### 1.4 LocationPickerModal — ปักหมุดบนแผนที่ (ฐานของข้อ 4, 5, 16)

**ทำ:** ติดตั้ง `leaflet@1.9.4` + `react-leaflet@5.0.0` + `@types/leaflet`
สร้างสองไฟล์

- `components/common/LocationPickerModal.tsx` แผนที่เต็มจอในกล่อง overlay
  คลิกปักหมุด ลากหมุดปรับตำแหน่ง ปุ่มใช้พิกัดปัจจุบัน และช่องอ่านค่า lat/lng
- `components/common/LocationPickerButton.tsx` ปุ่มที่ฟอร์มเรียกใช้
  โหลดแผนที่แบบ lazy

ต่อเข้า `AccidentForm` แล้วเป็นตัวแรก (ฟอร์มด่านกับจับกุมต่อในวันที่ 2 ตามแผน)
**ไม่ได้ลบปุ่ม "ดึงพิกัด" เดิมทิ้ง** ปุ่มนั้นยังเป็นทางที่เร็วที่สุดตอนเจ้าหน้าที่ยืนอยู่
ตรงจุดเกิดเหตุ ปุ่มปักหมุดมีไว้สำหรับรายงานที่พิมพ์ย้อนหลังที่หน่วย ซึ่งเดิมทำไม่ได้เลย
ต้องเปิด Google Maps อีกแท็บแล้วคัดลอกตัวเลขมาเอง

**ปัญหาที่เจอ 2 เรื่อง:**

1. **หน้าจอขาวและ console ขึ้น "Invalid hook call ... more than one copy of React"**
   ตอนเปิดแผนที่ครั้งแรก ตรวจแล้วพบว่า `npm ls react` มี React ตัวเดียว (19.2.8 deduped)
   ต้นเหตุจริงคือ Vite แคช pre-bundle ไว้คนละรุ่นหลังติดตั้งแพ็กเกจใหม่ (สังเกตจาก
   `react.js?v=2456b638` กับ `react-dom_client.js?v=ed7f865b` คนละ hash)
   แก้ด้วยการลบ `node_modules/.vite` แล้วรีสตาร์ต dev server **บันทึกไว้เพราะ
   อาการนี้ทำให้เข้าใจผิดว่าโค้ดผิดกฎ hook ทั้งที่เป็นเรื่องแคชล้วน ๆ**
2. **ไอคอนหมุดของ leaflet หายเป็นภาพแตกกับทุก bundler** เพราะ leaflet อ้าง path
   ของไฟล์ภาพแบบที่ bundler แก้ให้ไม่ได้ แก้ด้วยการ import ภาพทั้งสามไฟล์เข้ามา
   แล้วตั้ง `L.Marker.prototype.options.icon` เอง

**ทดสอบผ่านเบราว์เซอร์จริง:** เปิดฟอร์มอุบัติเหตุ กดปุ่มปักหมุด แผนที่โหลด 8 ไทล์
พร้อม attribution ของ OpenStreetMap คลิกกลางแผนที่ได้หมุด 1 ตัวและอ่านค่า
`16.459386 / 99.071838` กด "ใช้พิกัดนี้" แล้วค่าลงช่องละติจูด/ลองจิจูดของฟอร์ม
และ modal ปิดเอง

**ผลต่อขนาดไฟล์ (`npm run build` ผ่าน):**

| chunk | ขนาด | gzip |
|---|---|---|
| `LocationPickerModal` (แยกออกมา) | 162.35 kB | 51.61 kB |
| `index` (bundle หลัก) | 293.76 kB | 88.38 kB |

ตรวจแล้วว่า **ไม่มีคำว่า leaflet ใน bundle หลักเลย** คนที่แค่เปิดหน้าล็อกอินจึงไม่ต้อง

### 5.1 Modal ตรวจรายละเอียดก่อนอนุมัติ (ข้อ 9 เสร็จ)

**ปัญหาของเดิม:** หน้าแอดมินกดอนุมัติจากตารางได้เลย เห็นแค่ประเภทรายงานกับชื่อผู้ส่ง
ซึ่งแปลว่าการอนุมัติเป็นการกดผ่านโดยไม่ได้ตรวจอะไรจริง

**ทำ:** `GET /api/records/detail` + `RecordDetailModal` ปุ่มในตารางเปลี่ยนจาก
"อนุมัติ" เป็น "ตรวจ/อนุมัติ" ที่เปิดกล่องรายละเอียดก่อนเสมอ

**การตัดสินใจ:**

- **คืนทุกช่องที่มีค่า ไม่เลือกเฉพาะบางช่อง** เพราะแต่ละตารางมีฟิลด์คนละชุด
  และ requirement ขอให้เห็นครบ
- **ตัดช่องว่างออก** ตารางจับกุมมี 34 คอลัมน์ ถ้าโชว์ช่องเปล่าด้วย แอดมินต้องเลื่อน
  ผ่านสิบกว่าช่องกว่าจะเจอเนื้อรายงาน ซึ่งทำให้คนเลิกอ่านแล้วกดอนุมัติเลย
- **แยกไฟล์แนบออกมาเป็นปุ่มเปิดดู** ไม่ให้ต้องคัดลอกลิงก์ไปเปิดเอง ซึ่งเป็นขั้นตอน
  ที่คนจะข้ามแล้วกดอนุมัติโดยไม่ได้ดูของจริง
- **รายการที่ไม่มีไฟล์แนบขึ้นคำเตือนสีเหลือง** ไม่ใช่เว้นว่างไว้เฉย ๆ

### 5.2 แก้ไขรายการของตัวเอง (ข้อ 10 เสร็จ)

`query_service.update_record` + `POST /api/records/update` และหน้าประวัติเพิ่มปุ่ม
"ดู / แก้ไข" คู่กับปุ่มยกเลิกเดิม

**สามด่านที่กันไว้ พร้อมเหตุผล:**

1. **เจ้าของรายการเท่านั้น** แอดมินที่เห็นรายการนี้ก็แก้ไม่ได้ เพราะถ้าคนอื่นแก้เนื้อ
   รายงานแล้วชื่อผู้ส่งยังเป็นชื่อเดิม ร่องรอยความรับผิดชอบจะเพี้ยน ถ้าแอดมินเห็นว่าผิด
   ให้ตีกลับให้เจ้าตัวส่งใหม่
2. **เฉพาะรายการที่ยังเป็น Pending** เมื่ออนุมัติแล้วตัวเลขถูกนับเข้ารายงานของหน่วยไปแล้ว
   การแก้ย้อนหลังจะทำให้ยอดที่ส่งขึ้นไปกับยอดในระบบไม่ตรงกันโดยไม่มีใครรู้
3. **คอลัมน์ระบบแก้ไม่ได้** `Sys_Status` (แก้ได้ = อนุมัติตัวเอง) และ
   `Data_StationID` (แก้ได้ = ย้ายรายงานข้ามสถานี) อยู่ในรายการต้องห้าม

**เขียนเฉพาะช่องที่ค่าเปลี่ยนจริง ไม่เขียนทับทั้งแถว** เพราะชีตไม่มี row lock
การอ่านมาแล้วเขียนกลับทั้งแถวจะกลืนค่าที่คนอื่นเพิ่งแก้ระหว่างนั้น (มีเทสยืนยันว่า
เขียนแค่ 2 ช่วง คือช่องที่แก้กับ `Sys_LastUpdate`) และทุกการแก้ไขลง audit log

### 5.3 จัดกลุ่มข้อหาตาม พ.ร.บ. (ข้อ 14 เสร็จ)

`charge_group_service.py` + `GET /api/dropdowns/charges-grouped` +
`ChargeSelect` / `ChargeGroupToggle` ต่อเข้าฟอร์มจับกุมและตารางข้อหา ว.20

**ที่มาของกลุ่มมีสองทาง เรียงตามความน่าเชื่อถือ**

1. **คอลัมน์ F ในชีต `tb_Charges`** ถ้ามีคนกรอกไว้ ถือเป็นคำตอบสุดท้ายเสมอ
   รับได้ทั้ง "พ.ร.บ.จราจรทางบก" และ "จราจรทางบก" เพราะคนกรอกพิมพ์ไม่เหมือนกัน
2. **เดาจากคำในชื่อข้อหา** เมื่อคอลัมน์นั้นว่าง

**การเดาจากคำไม่ใช่คำตอบทางกฎหมาย** ข้อหาที่เดาไม่ได้ตกไป "ข้อหาเฉพาะทาง"
ซึ่งปลอดภัยกว่าการเดาผิดกลุ่ม **หน่วยควรไล่กรอกคอลัมน์ F ให้ครบก่อนใช้จริง**

ข้อหา **"บุคคลต่างด้าว (ที่เกี่ยวกับ Scammer)"** เก็บเป็น built-in ในโค้ดและผสมเข้า
รายการเสมอแม้ยังไม่มีในชีต เพราะการเพิ่มแถวลงชีตต้องมี credentials ของ Google
ซึ่งเครื่องที่พัฒนาไม่มี ถ้าแอดมินเพิ่มลงชีตเองแล้วจะไม่แสดงซ้ำเพราะเทียบด้วยชื่อ

**`get_charges()` เดิมยังคืนลิสต์ของสตริงเหมือนเดิม** ฟอร์มที่ยังไม่ต้องการกลุ่ม
จึงไม่ต้องแก้ตาม

### 5.4 Filter ฐานความผิดบน Dashboard (ข้อ 6 เสร็จ)

`AnalysisPanel` เพิ่มตัวกรองสองชั้น: เลือกกลุ่ม พ.ร.บ. และค้นหาชื่อข้อหา

**การตัดสินใจ: ตัวกรองมีผลกับ "รายการที่เห็น" เท่านั้น ไม่ล้างสิ่งที่ติ๊กไว้แล้ว**
การกรองแล้วลบตัวเลือกทิ้งเงียบ ๆ จะทำให้ผลลัพธ์ไม่ตรงกับที่ผู้ใช้คิดว่าเลือกไว้

ป้ายบอกทั้งสองตัวเลข (เลือกไว้กี่ตัว / แสดงกี่ตัวจากทั้งหมด)

### 6.2 เกณฑ์คุณภาพสื่อ 1080p (FR-02, BR-01)

ตรวจสองชั้น: เบราว์เซอร์วัดด้วย `Image()` / `HTMLVideoElement` ก่อนอัป
แล้ว backend ตรวจภาพซ้ำด้วย Pillow

**สามการตัดสินใจที่สำคัญ:**

1. **วัดด้านสั้น ไม่ใช่ความสูง** สื่อจากมือถือเป็นแนวตั้ง (1080x1920) การเช็คแค่
   ความสูงจะตกภาพแนวนอนที่ถูกต้อง (1920x1080) ส่วนการเช็คแค่ความกว้างจะตกแนวตั้ง
2. **ขนาดที่อ่านไม่ได้ถือว่า "ไม่ผ่าน"** จุดประสงค์ของเกณฑ์คือให้คนมาดูของที่ระบบ
   ไม่มั่นใจ การปล่อยผ่านสิ่งที่วัดไม่ได้ทำให้เกณฑ์นี้ไม่มีความหมาย
3. **ค่าจาก Pillow ชนะค่าจากเบราว์เซอร์เสมอ** เพราะค่าจากหน้าเว็บแก้ได้ด้วย DevTools
   (มีเทสยืนยันว่าไฟล์ 640x480 ที่อ้างว่าเป็น 1920x1080 ถูกจับได้)

**สื่อที่ไม่ผ่านไม่ได้ทำให้ข่าวถูกปฏิเสธ** แต่ทำให้ข่าวติดธงรอพิจารณาตาม BR-01
การทิ้งงานของเจ้าหน้าที่เพราะภาพความละเอียดต่ำจะทำให้ไม่มีใครส่งข่าวเข้าระบบ

**เพิ่ม `pillow` ใน requirements.txt** พร้อมคอมเมนต์ว่าวิดีโอยังเชื่อค่าจากเบราว์เซอร์
เพราะ Render แผนฟรีไม่มี ffprobe

# รอบไล่ตรวจทั้งระบบ (frontend ทุกหน้า + backend ทุก endpoint)

## ปัญหาของวิธีทดสอบเดิม

รอบก่อนหน้าทดสอบ frontend ด้วยการดักคำขอ API แล้วตอบข้อมูลปลอมกลับไป
วิธีนั้นพิสูจน์ได้แค่ว่าหน้าเว็บวาดถูกเมื่อได้ข้อมูลรูปที่คาดไว้ แต่พิสูจน์ไม่ได้เลยว่า

- ชื่อฟิลด์ที่ frontend ส่ง ตรงกับที่ backend รับจริงหรือไม่
- ข้อมูลที่กรอกไปลงชีตใบไหน คอลัมน์ไหน
- การตรวจสิทธิ์ทำงานจริงตอนยิงผ่าน HTTP

## สิ่งที่ทำ

สร้าง `scripts/dev_server_fake_sheets.py` — รัน `app.main` ตัวจริงทั้งก้อน แล้วสลับ
เฉพาะสามชั้นที่คุยกับโลกภายนอกออกเป็นตัวจำลองในหน่วยความจำ (`sheets_service`,
`storage_service`, `line_service`) ทุกอย่างที่เหลือคือของจริง

ตัวจำลองบันทึกทุกการเขียน **พร้อมจับคู่ค่ากับชื่อคอลัมน์** และบันทึกทุกตารางที่ถูกอ่าน
จึงตอบได้ตรง ๆ ว่าแต่ละช่องกรอกไปลงช่องไหน

เหตุผลที่ไม่ใช้ Google จริง: เครื่องพัฒนาไม่มีสิทธิ์เข้าสเปรดชีตของหน่วย และต่อให้มี
การยิงทดสอบ 62 ครั้งรวดจะกินโควตา 60 คำขอ/นาที ที่ทั้งระบบใช้ร่วมกันจนหน่วยอื่นใช้ไม่ได้

จากนั้นเขียน `scripts/sweep_endpoints.py` ยิงทุก endpoint ที่ frontend เรียก
โดยใช้ payload รูปเดียวกับที่ฟอร์มจริงส่ง

## ผลที่ได้

**62 กรณี ผ่าน 61** — ที่เหลือคือ `POST /api/commander/order` ตอบ 502 เพราะยังไม่ได้ตั้ง
`lineGroupId` ของสถานีปลายทาง ซึ่งเป็นเรื่องคอนฟิก ไม่ใช่บั๊ก

## ปัญหาที่เจอระหว่างทาง

**เกือบสรุปผิดว่าโค้ดพัง ทั้งที่ตัวจำลองไม่ครบ** — รอบแรก `/admin/reference/charges`
ตอบสำเร็จแต่ไม่มีอะไรลงชีต แล้วคำสั่งถัดไปหาแถวนั้นไม่เจอ ดูเหมือน backend พัง
ที่จริง `FakeWorksheet.update()` เขียนไว้เป็น `return {}` เฉย ๆ เส้นทางที่ใช้ `worksheet.update`
จึงหายไปเงียบ ๆ แก้ตัวจำลองให้เขียนจริงแล้วผ่าน

บทเรียน: ตัวจำลองที่ไม่ครบทำให้กล่าวหาโค้ดที่ถูกต้อง ก่อนสรุปว่าเป็นบั๊กต้องไล่ดูก่อนว่า
เส้นทางนั้นวิ่งผ่านอะไรที่เราจำลองไว้ไม่ครบหรือเปล่า

**สคริปต์ทดสอบเองผิดหลายจุดจนดูเหมือนระบบพัง** — ส่ง `teamArray` เป็น object
ทั้งที่ schema รับ `List[str]`, ส่ง `headline` ทั้งที่ backend อ่าน `title`, ส่ง `q=` ทั้งที่
API รับ `keyword=` และเรียกด้วยบทบาทที่ไม่มีสิทธิ์ ทุกจุดตรวจแล้วพบว่า frontend
กับ backend ตรงกันอยู่แล้ว ผิดที่สคริปต์ทดสอบล้วน ๆ

หลังแก้ ปรับสคริปต์ให้ถือว่า HTTP 200 ที่มี `status: "error"` เป็นไม่ผ่านด้วย
เพราะรอบแรกความผิดพลาดเชิงธุรกิจถูกกลบไปกับรหัส 200

**ตัวเลข "ไม่อ่านชีต" ครั้งแรกเชื่อไม่ได้** — endpoint หลายตัวรายงานว่าไม่แตะชีตเลย
ที่จริงถูกเสิร์ฟจากแคชในหน่วยความจำ (`user_service._cache` และแคชแถวของ `query_service`)
ต้องล้างแคชทุกชั้นก่อนวัดใหม่ ถึงได้ตัวเลขที่ตรงกับความจริง

## บั๊กจริงที่เจอ 4 จุด

1. `GET /api/health/database` ตอบ 500 เมื่อเปิดสเปรดชีตไม่ได้ — gspread โยน
   `SpreadsheetNotFound` ที่ไม่ได้สืบทอด error ของโปรเจกต์ จึงหลุด `except` ทั้งที่
   endpoint นี้มีไว้บอกว่ากองไหนเปิดไม่ได้พอดี หน้าผู้บังคับการเลยค้าง "กำลังตรวจสอบ"

2. endpoint เดียวกันไม่มีการจำกัดสิทธิ์เลย มีแค่ `current_session` ผู้ปฏิบัติทุกคนจึง
   อ่านรหัสสเปรดชีตของทุกกองกับอีเมลบัญชีบริการได้ เจอจากการเขียนเทสสิทธิ์คู่กับข้อ 1

3. ตารางประวัติการส่งอ่านไม่ออกทั้งใบ พื้นขาวทึบตัวหนังสือขาว — `<style>` ที่ Apps Script
   scope ไว้ที่ `#formMyHistory` ไม่ได้ถูกย้ายมาตอนพอร์ต ตารางอื่นอีก 26 จุดในระบบ
   ใช้คลาส `table-sc`/`table-hq` อยู่แล้ว ใบนี้เป็นใบเดียวที่หลุด

4. ช่องวันที่ภาษาไทยค้างค่าเดิมเมื่อฟอร์มเปลี่ยนค่าจากข้างนอก — โค้ดเทียบกับ
   `fp.input.value` แต่ input ตัวนั้นเป็นของ React ซึ่งเขียนค่าใหม่ตั้งแต่ตอน commit
   ที่เกิดก่อน effect เสมอ ค่าจึงเท่ากันทุกครั้ง `setDate` ไม่เคยถูกเรียก ผลคือช่อง ISO
   เปลี่ยนตามแต่ช่องที่เจ้าหน้าที่มองเห็นค้างวันเดิม

ข้อ 4 เป็นบั๊กที่อันตรายที่สุดในสี่ข้อ เพราะไม่มีอะไรฟ้อง เจ้าหน้าที่กดปุ่ม "เวลาปัจจุบัน"
เห็นวันเดิมค้างอยู่ก็นึกว่าปุ่มไม่ทำงาน แต่ค่าที่ส่งเข้าระบบเปลี่ยนไปแล้วจริง ๆ

## ทางเดินมือถือของช่องวันที่

`ThaiDateInput` แยกทางเดินตามขนาดจอ ฝั่งมือถือไม่เคยถูกรันเลยตลอดโครงการ
พยายามย่อหน้าต่าง Chrome ลงต่ำกว่า 769px แล้วแต่ `window.innerWidth` ไม่ขยับตาม
จึงเปลี่ยนไปคุมด้วยเทสแทน (7 เคส ครอบทั้งสองทางเดิน) ซึ่งได้ผลดีกว่าเพราะเป็นการคุมถาวร
ไม่ใช่การกดดูครั้งเดียว — และเทสข้อสุดท้ายจับบั๊กข้อ 4 ข้างบนได้จริง

### การตัดสินใจเรื่องสิทธิ์บน Drive

แผนเดิมบอกว่า FR-07/08 ติดตรงที่ "ต้องตัดสินใจเรื่องสิทธิ์ไฟล์บน Drive ก่อน" เพราะ
`แผนย้ายไปฐานข้อมูลจริง.md` หัวข้อ 8 บันทึกไว้ว่ามีไฟล์ 20 รายการตั้งเป็น
"ทุกคนที่มีลิงก์แก้ไขได้" รวมแท็บที่เก็บชื่อจริงและเบอร์โทรเจ้าหน้าที่

สิ่งที่เลือกทำ กติกาสี่ข้อ เขียนไว้เป็นค่าคงที่ในโค้ดไม่ใช่แค่ในเอกสาร

1. สิทธิ์ที่ให้คือ `{"type": "anyone", "role": "reader"}` เท่านั้น — `writer` ไม่มี
   กรณีไหนที่มีเหตุผลรองรับสำหรับข่าวที่แจกออกไปแล้ว
2. ให้สิทธิ์ที่ **ตัวไฟล์ชิ้นงาน** ไม่ใช่ที่โฟลเดอร์ โฟลเดอร์เดียวกันนั้นมีภาพจาก
   ที่เกิดเหตุปนอยู่ การเปิดทั้งโฟลเดอร์เพื่อแจกข่าวใบเดียวคือการเปิดของทั้งกอง
3. สร้างลิงก์ได้เฉพาะข่าวที่ **อนุมัติแล้ว** ไม่งั้นคิวอนุมัติของ FR-09 ก็ข้ามได้ด้วย
   การกดปุ่มแชร์แทน
4. มีปุ่มถอนลิงก์อยู่ในหน้าเดียวกัน ลิงก์ที่ปิดไม่เป็นคือลิงก์ที่เปิดค้างตลอดไป

ไม่ใช่แค่รีวิวด้วยตา เพราะการเผลอเปลี่ยนเป็น `writer` ในอนาคตจะเงียบสนิท

### แยกปุ่ม "ประกอบชิ้นงาน" ออกจาก "สร้างลิงก์"

รอบแรกคิดจะทำปุ่มเดียว กดแล้วได้ลิงก์เลย แต่แบบนั้นทุกครั้งที่เจ้าหน้าที่อยากลองดูว่า
เทมเพลตออกมาหน้าตายังไงจะกลายเป็นการเผยแพร่จริงไปด้วย จึงแยกเป็นสองขั้น
`POST /api/pr/news/compose` คืนข้อความอย่างเดียวไม่แตะ Drive ส่วน
`POST /api/pr/news/share` ถึงจะอัปไฟล์และเปิดสาธารณะ

### สร้างลิงก์ใหม่ต้องถอนของเก่า

คอลัมน์ `Share_File_ID` เก็บได้ทีละหนึ่ง ถ้าสร้างลิงก์ใหม่ทับโดยไม่ถอนของเก่า
ไฟล์รุ่นเดิมจะยังเปิดสาธารณะอยู่โดยไม่มีร่องรอยว่ามันอยู่ที่ไหน endpoint จึงถอน
สิทธิ์ของไฟล์เดิมก่อนเขียนทับเสมอ

## ที่ต้องแก้ระหว่างทาง

**`query_service.update_record` ปฏิเสธการเขียนลงแถวที่อนุมัติแล้ว** ซึ่งถูกต้องสำหรับ
requirement ข้อ 10 แต่ FR-08 ต้องเขียนลิงก์ลงแถวที่อนุมัติแล้วเป็นปกติ แทนที่จะผ่อนกฎ
ของข้อ 10 แยกชั้นล่างออกมาเป็น `write_columns()` ที่รู้แค่วิธีเขียนลงชีตอย่างปลอดภัย
แล้วให้ `update_record` เป็นชั้นบนที่ตรวจสถานะก่อนเรียกมัน ทั้งสองงานใช้กลไกเดียวกัน
โดยไม่มีใครต้องผ่อนกฎของอีกฝั่ง

**เทสจับได้ว่าลืมต่อแถว** — เพิ่มสี่คอลัมน์ใน schema แล้ว `prepare_news` ยังสร้างแถว
ยาว 23 ช่องเท่าเดิม `test_row_matches_the_schema` ที่มีอยู่แล้วฟ้องทันที (23 != 27)
เป็นเทสที่เขียนไว้รอบที่แล้วและคุ้มค่าที่สุดในรอบนี้

## FR-10 — รายงานข่าวค้างอนุมัติแยกตามสังกัด

จัดกลุ่มตาม `Data_UnitID` ข่าวที่ไม่มีหน่วยกำกับตกไปอยู่กลุ่มของสถานีแทนที่จะหายไป
ข่าวที่หายจากรายงานค้างอนุมัติคือข่าวที่ไม่มีใครอนุมัติให้ตลอดกาล

เรียงหน่วยตาม **ใบที่ค้างนานที่สุด** ไม่ใช่ตามจำนวน คนเปิดรายงานนี้เปิดเพื่อหาว่า
ต้องไปตามใคร ค้าง 20 ใบที่เพิ่งส่งเมื่อเช้าคือคิวปกติ ค้าง 3 ใบมาเก้าวันแปลว่ามีคนลืม
แบ่งช่วงอายุเป็นสี่ถัง (วันนี้ / 1-3 / 4-7 / เกิน 7) และแสดงจำนวนวันเป็นตัวเลขคู่กับสี
เสมอ เพราะสีอย่างเดียวคนตาบอดสีอ่านไม่ออก

วันที่ที่อ่านไม่ได้นับเป็น 0 วัน ไม่ใช่ปล่อยให้คำนวณพัง ข้อมูลเสียหนึ่งแถวต้องไม่ทำให้
รายงานขึ้นว่ามีข่าวค้างมาห้าหมื่นวัน
