## 1. สรุปสำหรับผู้บริหาร

ก่อนเริ่มงาน ระบบรับข้อมูลจากฟอร์มได้แต่**ไม่ได้บันทึกลงที่ใดเลย** โค้ดฝั่งเซิร์ฟเวอร์เตรียมแถวข้อมูลไว้ครบแล้วโยนทิ้ง และหน้าเว็บแสดงข้อความว่าบันทึกสำเร็จทุกครั้งแม้เชื่อมต่อไม่ได้ ทำให้เจ้าหน้าที่เชื่อว่าส่งรายงานแล้วทั้งที่ข้อมูลหายไป

ตอนนี้ฟอร์มทั้ง 14 ประเภททำงานครบ ระบบยืนยันตัวตนก่อนเขียนข้อมูลทุกครั้ง และเมื่อบันทึกไม่สำเร็จจะแจ้งเป็นข้อผิดพลาด ไม่แจ้งว่าสำเร็จอีกต่อไป

ฝั่งอ่านข้อมูลก็ไม่มีมาก่อนเช่นกัน รายงานส่งเข้าไปได้แต่ไม่มีใครอนุมัติได้ เพราะทุก endpoint ที่หน้า dashboard เรียกยังไม่มีอยู่จริง ตอนนี้คิวอนุมัติ ประวัติการส่ง รายการภารกิจ ตัวเลือกใน dropdown และหน้าสรุปยอดระดับสถานี กองกำกับ และประเทศ ทำงานครบแล้ว

การล็อกอินตรวจกับแท็บ `tb_Users` ในชีตกลางแล้ว ไม่มีบัญชีหรือรหัสผ่านฝังอยู่ในโค้ดทั้งฝั่งเซิร์ฟเวอร์และหน้าเว็บอีกต่อไป รหัสผ่านทั้ง 58 บัญชีเก็บเป็น `sha256$` หมดแล้ว และโหมดสาธิตต้องเปิดด้วยการตั้งค่าตอน build เท่านั้น

## 3. งานด้านความปลอดภัย

**บังคับให้ `SESSION_SECRET` มาจาก environment**
ถอดค่าเริ่มต้นออกทั้งหมด ระบบไม่ยอมเริ่มทำงานถ้าไม่ได้ตั้งค่า และขึ้นบัญชีดำค่าเดิมสองตัวที่เคยอยู่ใน git ไว้ ถ้ามีคนนำกลับมาใช้ระบบจะปฏิเสธ

**ตรวจ session ทุกครั้งก่อนเขียนข้อมูล**
ทั้ง 3 ปลายทางตรวจ token จริง ไม่มี token หรือ token ปลอมได้ HTTP 401

**ตรวจสิทธิ์ระดับสถานี**
รหัสสถานีที่ส่งมาต้องอยู่ในขอบเขตที่ session นั้นมองเห็นได้ ตามกฎเดิมของระบบ (สถานีตรงกัน / ฝอ.กก. เห็นทั้งกองกำกับ / ส่วนกลางเห็นทั้งประเทศ) ส่งข้ามสถานีได้ HTTP 403

**ตรวจไฟล์แนบ**
จำกัด 10 ไฟล์ต่อรายงาน ไฟล์ละไม่เกิน 10 MB รับเฉพาะรูปภาพและ PDF ล้างชื่อไฟล์กัน path traversal

**ปิดช่องโหว่ formula injection**
เขียนข้อมูลด้วยโหมด `RAW` ทำให้ข้อความที่ขึ้นต้นด้วย `=` ไม่ถูกคิดเป็นสูตร

**หน้าเว็บจัดการ session หมดอายุ**
ถอด session ที่หมดอายุตั้งแต่โหลดหน้า และเมื่อเซิร์ฟเวอร์ตอบ 401 จะพากลับไปหน้าเข้าสู่ระบบพร้อมข้อความที่อ่านเข้าใจ

## 4. ชั้นบันทึกข้อมูล

**การยืนยันตัวตนกับ Google**
องค์กรบล็อกการสร้าง service account key (`iam.disableServiceAccountKeyCreation`) จึงใช้ OAuth ในนามบัญชี `marsocas.1998@gmail.com` แทน ระบบรองรับทั้งสองแบบ เลือก OAuth ก่อนถ้าตั้งค่าครบ

สถานะแอปใน Google Cloud ถูกเปลี่ยนเป็น **In production** แล้ว ทำให้ refresh token ไม่หมดอายุใน 7 วันแบบสถานะ Testing

**นิยามโครงสร้างตาราง** (`app/core/schema.py`)
หัวคอลัมน์คัดลอกจากชีตจริงที่ Apps Script สร้างไว้ ทุกตารางขึ้นต้นด้วย 9 คอลัมน์มาตรฐานตามพิมพ์เขียว มีชุดทดสอบตรวจว่าจำนวนช่องข้อมูลที่โค้ดสร้างตรงกับจำนวนคอลัมน์เสมอ ถ้าใครเพิ่มฟิลด์แล้วลืมแก้อีกฝั่ง ชุดทดสอบจะฟ้องทันที แทนที่จะปล่อยให้ข้อมูลลงผิดช่องเงียบ ๆ

**ตัวเขียนข้อมูล** (`app/services/sheets_service.py`)
สร้างแท็บพร้อมหัวคอลัมน์ให้อัตโนมัติถ้ายังไม่มี จำ handle ของแท็บไว้ใช้ซ้ำเพื่อประหยัดโควตา และรอแล้วลองใหม่เมื่อ Google ตอบว่าเกินโควตาชั่วคราว

**ลำดับการทำงานที่แก้ใหม่**
เดิมส่ง LINE ก่อนแล้วตอบสำเร็จโดยไม่สนใจว่าบันทึกได้หรือไม่ ตอนนี้ต้องเขียนชีตสำเร็จก่อน จึงจะส่ง LINE และตอบสำเร็จ ถ้าเขียนไม่ได้จะตอบ 503 (ยังไม่ตั้งค่า) หรือ 502 (Google ปฏิเสธ) พร้อมเหตุผลภาษาไทย ส่วนกรณีส่ง LINE ไม่ผ่านจะบันทึกไว้ในบันทึกระบบเฉย ๆ ไม่ทำให้รายงานที่บันทึกแล้วกลายเป็นข้อผิดพลาด

**เครื่องมือ**

| สคริปต์ | หน้าที่ |
|---|---|
| `scripts/get_oauth_token.py` | ขอ refresh token และเขียนลง `.env` ให้ |
| `scripts/setup_database.py` | สร้างสเปรดชีตและแท็บของแต่ละ กก. รันซ้ำได้ไม่สร้างซ้ำ |
| `scripts/verify_dataflow.py` | ตรวจการไหลของข้อมูลทั้งระบบ |
| `GET /api/health/database` | รายงานสถานะการเชื่อมต่อรายกองกำกับ |

## 6. ฝั่งอ่านข้อมูลและหน้า dashboard

รายงานส่งเข้าไปได้แต่ไม่มีใครอนุมัติได้ เพราะทุก endpoint ที่หน้า dashboard เรียกยังไม่มีอยู่จริง ทุกคำขอตกลงไปใน `catch` ที่คืนลิสต์ว่าง หน้าเว็บจึงแสดง dropdown ว่างเปล่าโดยไม่มี error

**ตัวเลือกใน dropdown และการเปลี่ยนรหัสผ่าน**
`dropdowns/units` อ่านจาก `STATION_CONFIG` ส่วนชื่อและเบอร์เจ้าหน้าที่อ่าน `tb_Users` และข้อหาอ่าน `tb_Charges` ผ่าน `reference_service` ที่พักข้อมูลไว้ 5 นาทีแบบเดียวกับ `user_service` ทั้งห้าเส้นทางต้องมี session เพราะ `/users` กับ `/user-phones` คืนชื่อจริงและเบอร์โทร ถ้าไม่ตรวจ ใครก็ไล่เก็บข้อมูลของสถานีไหนก็ได้

`change-password` เก็บเป็น `sha256$` เสมอไม่ว่าบัญชีนั้นเดิมเก็บแบบใด และปฏิเสธ token ที่เป็นของบัญชีอื่น ถือ token ของ ผบก. ก็ตั้งรหัสให้คนอื่นไม่ได้

**คิวอนุมัติ ประวัติ และรายการภารกิจ**
`query_service` เป็นคู่ฝั่งอ่านของ `report_service` อ่านค่าตามตำแหน่งคอลัมน์ตาม `schema.py` ไม่ใช่ตามหัวคอลัมน์ในชีต เพราะชีตที่ Apps Script สร้างไว้มีป้ายบางช่องไม่ตรงกับข้อมูลใต้ป้าย (ดูหัวข้อ 8) ตารางที่ยังไม่เคยถูกเขียนจะยังไม่มีแท็บ กรณีนี้อ่านออกมาเป็นคิวว่าง ไม่ใช่ error

หน้า Admin ทั้งหน้าอ่านครั้งเดียวจบด้วย `station_overview` เดิมแยกอ่านคิว ยอดรวม และรายการที่อนุมัติวันนี้ กลายเป็นอ่านตารางเดิมซ้ำ 16 ครั้งต่อการเปิดหน้าหนึ่งครั้ง ซึ่งชนเพดาน 60 ครั้งต่อนาทีของ Google ตั้งแต่รอบทดสอบจริงรอบแรก

การอนุมัติเขียน `Sys_Status` กับ `Sys_LastUpdate` เป็นชุดเดียวที่ข้าม `Sys_ActionBy` ที่คั่นอยู่ตรงกลาง ชื่อผู้รายงานจึงถูกทับด้วยค่าที่อ่านมาก่อนหน้าไม่ได้ รายการที่ไม่ได้อยู่สถานะรออนุมัติจะแจ้งกลับ ไม่ใช่อนุมัติซ้ำ ส่วนการยกเลิกเปิดให้เจ้าของรายการทำเองได้ก่อนอนุมัติ และให้ผู้มีสิทธิ์อนุมัติทำได้ในขอบเขตของตน ทั้งสองทางยังผ่านการตรวจสถานีเหมือนเดิม

**หน้าสรุปยอด**
`daily-summary` เติมแท็บสรุปของฟอร์มรายงานประจำวัน ส่วน `division-summary` รองรับหน้า ฝอ.กก. และหน้าผู้บังคับบัญชา ให้ยอดรายสถานี ของกลาง ข้อหา สาเหตุอุบัติเหตุ และแนวโน้มรายวัน ทุกสถานีใน กก. เดียวกันใช้สเปรดชีตไฟล์เดียวกัน จึงอ่านแต่ละตารางครั้งเดียวแล้วค่อยแยกตามสถานี ไม่ใช่วนเรียกทีละสถานีหกรอบกับไฟล์เดิม

ยอดทั้งหมดนับเฉพาะแถวที่ผ่านการตรวจแล้ว ถ้านับแถวที่ยังรออนุมัติด้วย ตัวเลขบนการ์ดจะกระโดดทันทีที่มีคนกดส่ง แล้วลดลงอีกครั้งเมื่อผู้ดูแลตีกลับ ซึ่งดูเหมือนระบบนับผิด

**การรวมยอดระดับประเทศ**
หน้าระดับประเทศครอบคลุม 8 กก. ที่อยู่คนละสเปรดชีต การอ่านสดคือ 48 คำขอต่อการเปิดหน้าหนึ่งครั้ง ผู้บังคับบัญชาสองคนเปิดพร้อมกันก็ชนเพดานกันเอง จึงแยกตามที่ Apps Script ตั้งใจไว้ คือให้ตัวตั้งเวลารวมยอดลง `tb_National_Summary` แล้วหน้าเว็บอ่านตารางเดียว

`aggregate_national` เขียนทับแถวเดิมของคู่ (วันที่, กก.) ไม่ใช่ต่อท้าย ตัวเดิมใน Apps Script ต่อท้ายทุกรอบ ตารางจึงสะสมไว้ 803 แถวสำหรับข้อมูลจริงเพียง 34 คู่ บางวันซ้ำกันถึง 24 ชุด อ่านตรง ๆ จะได้ตัวเลขคูณตามจำนวนรอบที่ตัวตั้งเวลาเคยทำงาน ตัวอ่านจึงเก็บแถวสุดท้ายของแต่ละคู่ และตัวรวมยอดตีตราแถวเก่าเป็นไม่ใช้งานระหว่างทาง มี `--dedupe` ไว้ล้างของเก่าที่ค้าง รันแล้วเหลือ 34 แถวใช้งานจาก 770 แถว โดยตีตราไม่ใช้งานแทนการลบ ตัวเลขเดิมจึงยังอ่านย้อนได้

**บัญชีหน่วยไม่ปนในช่องผู้รายงาน**

## 8. บั๊กที่พบและแก้ไข

**เบอร์โทรสูญเสียเลข 0 นำหน้า**
`0812345678` ถูกบันทึกเป็น `812345678` เพราะส่งข้อมูลด้วยโหมดที่ให้ Google ตีความค่าใหม่แล้วอ่านเป็นตัวเลข แก้เป็นโหมด `RAW` ที่เก็บค่าตามที่ส่งไป

**ข้อมูลเดิมใน `DB_TEST_กก.1` ที่ Apps Script เขียนไว้มีปัญหาเดียวกัน** คอลัมน์เบอร์โทรทุกแถวขาดเลข 0 นำหน้า เป็นข้อบกพร่องที่มีมาก่อนหน้านี้ ควรพิจารณาแก้ข้อมูลเดิมและแก้ฝั่ง Apps Script ด้วยหากยังใช้งานคู่กัน

**เกินโควตาการอ่านของ Google**
ระบบอ่านโครงสร้างแท็บใหม่ทุกครั้งที่บันทึก ทำให้ชนเพดาน 60 ครั้งต่อนาที และรายงานของ กก.8 บันทึกไม่สำเร็จ แก้โดยจำ handle ของแท็บไว้ใช้ซ้ำ และรอแล้วลองใหม่เมื่อเจอโควตาเต็ม ทดสอบซ้ำแล้วผ่านครบทั้ง 8

**ข้อผิดพลาดของ Google หลุดออกมาเป็น HTTP 500**
แปลงให้เป็น 502 พร้อมข้อความภาษาไทยที่บอกวิธีแก้

**ชื่อฟิลด์ไฟล์แนบไม่ตรงกัน**
หน้าเว็บส่งชื่อ `files` แต่เซิร์ฟเวอร์รอรับ `fileDataArray` ไฟล์จึงถูกทิ้งโดยไม่มีการแจ้ง แก้ให้ตรงกัน และตั้งค่าให้ชื่อฟิลด์ที่ไม่รู้จักตอบ 422 แทนการทิ้งเงียบ

**สคริปต์ตั้งค่าฐานข้อมูลไม่อ่านไฟล์ `.env`**
แก้ให้ตัวเขียนข้อมูลโหลดค่าตั้งค่าเองไม่ว่าจะถูกเรียกจากทางใด

**รหัสรายงานซ้ำกันได้**
รหัสเดิมประกอบด้วยวันที่ระดับนาทีกับเลขสุ่ม 3 หลัก ตอนทดสอบส่งรายงานจาก 8 กก. พร้อมกัน มีสองใบได้รหัส `CHK-260726-2211-869` เหมือนกัน โอกาสชนราว 3% ต่อการส่งพร้อมกัน 8 ใบในนาทีเดียว

เรื่องนี้สำคัญเพราะการอนุมัติและการยกเลิกอ้างอิงด้วยรหัสรายงาน ถ้าชนกันในชีตเดียวกันจะไปดำเนินการกับใบผิด แก้เป็นวันที่ระดับวินาทีกับเลขสุ่ม 6 หลัก โอกาสชนเหลือประมาณ 0.003% (รูปแบบใหม่ `OP-260726-221145-482913`) ข้อมูลเดิมที่ใช้รูปแบบเก่าไม่ได้รับผลกระทบ

**ชุดทดสอบอ่านค่าจริงจากเครื่องผู้พัฒนา**
หลังจากตั้งค่าใช้งานจริง ชุดทดสอบเดิมเริ่มล้มเหลวเพราะไปหยิบค่าจริงมาใช้ แก้ให้แต่ละชุดกำหนดสภาพแวดล้อมของตัวเองให้ชัดเจน

**ข้อหาถูกเขียนไว้สองแบบ อ่านด้วยตัวเดียวกันไม่ได้**
การจับกุมเขียนข้อหาบรรทัดละหนึ่งข้อพร้อมลำดับเลข ส่วนผลการปฏิบัติประจำวันเขียนรวมบรรทัดเดียวเป็น `ขับเร็ว (12) | ไม่สวมหมวก (5)` โดยตัวเลขคือจำนวนใบสั่งที่ออก อ่านแบบหลังด้วยตัวอ่านของแบบแรกทำให้ทั้งช่องกลายเป็นข้อหาเดียวที่ตั้งชื่อตามข้อความทั้งก้อน `ขับเร็ว` จึงโผล่สองครั้งใต้ป้ายคนละแบบ และจำนวนใบสั่งหายไปทั้งหมด เจอตอนรันกับข้อมูลจริง ชุดทดสอบไม่จับ

**ของกลางแบบมีโครงสร้างไม่เคยถูกอ่าน**
ฟอร์มจับกุมส่ง `seizedItems` มาเป็นอาร์เรย์ของตัวเองแยกจาก `formData` แต่ไม่มีใครอ่าน คอลัมน์ของกลางแบบมีโครงสร้างจึงว่างเสมอ และกราฟโดนัทของกลางทั้งสองอันจะขึ้นเป็นช่องว่าง ตอนนี้ endpoint ส่งค่าต่อและ `report_service` แปลงเป็นข้อความให้ ส่วนคอลัมน์ข้อความอิสระที่อยู่ข้างกันเจ้าหน้าที่แก้ได้เอง จึงเอามาใช้นับสถิติไม่ได้

**ป้ายหัวคอลัมน์ในชีตเดิมไม่ตรงกับข้อมูล** (ไม่ได้แก้ข้อมูลเดิม)
- `tb_DailyReport` ช่องที่ 14 เขียนว่า "รถวิทยุตรวจเขต" ซ้ำกับช่อง 13 ทั้งที่ข้อมูลที่บันทึกคือชื่อพลขับ

| สรุปผลภารกิจ | `reports/mission-summary` | ไม่เขียนตาราง รวมภารกิจที่บันทึกไว้แล้วส่งเข้า LINE ตรงตาม `sendMissionSummaryLine` ของเดิม |
| ออกเอกสารจับกุม | `reports/auto-arrest` | คัดลอกแม่แบบ Google Docs แล้วแทนค่า ได้บันทึกจับกุม 1 ฉบับ กับ ม.22/23 ตามจำนวนผู้ต้องหา |

`auto-arrest` มีสองเรื่องที่เจอตอนรันกับของจริง หน้าเว็บส่งชื่อฟิลด์ `respOfficer`/`respPhone` แต่แม่แบบเขียนว่า `RESPONSIBLE_OFFICER_NAME`/`_PHONE` บรรทัดนั้นจะพิมพ์ออกมาว่าง ตอนนี้รับทั้งสองแบบ และการคัดลอกเอกสารเกิดก่อนการแทนค่า รอบแรกล้มเหลวคั่นกลางเพราะยังไม่ได้เปิด Google Docs API ทิ้งเอกสารที่ยังมี `<<PLACEHOLDER>>` ครบทุกตัวไว้ปนกับเอกสารจริง ตอนนี้ลบสำเนาที่ทำไม่สำเร็จทิ้ง เก็บเฉพาะฉบับที่เสร็จ และแปลงข้อผิดพลาดที่พบบ่อยเป็นข้อความที่ผู้ดูแลลงมือแก้ได้ แทนการโยน `HttpError` ดิบออกมา

**แม่แบบบันทึกจับกุมมีตัวยึดแค่ 6 ตัว** ไม่มีช่องเจ้าหน้าที่ผู้รับผิดชอบ ผู้แจ้ง และสถานที่ควบคุมตัว (ฉบับ ม.22/23 มีครบ 15 ตัว) ระบบส่งค่าเหล่านั้นไปให้อยู่แล้ว เพิ่มตัวยึดลงในแม่แบบเมื่อไหร่จะถูกเติมเองโดยไม่ต้องแก้โค้ด

### 9.3 ข้อมูลสถานีครบทั้ง 8 กก. แล้ว

เดิมมีชื่อจังหวัดและรายชื่อหน่วยบริการจริงแค่ กก.1 กับ กก.5 ที่เหลือใช้ชื่อที่ระบบสร้างขึ้นเอง ตอนนี้ทั้ง 8 กก. ใช้ข้อมูลจริง และสร้างบัญชีใน `tb_Users` ครบ 52 บัญชี แยกเป็นสถานี 43 กองกำกับ 8 และระดับ บก. 1 ชื่อที่แสดงและข้อความแจ้ง LINE จึงเป็นชื่อหน่วยจริง

### 9.4 รหัสผ่านเข้ารหัสครบแล้ว

รหัสผ่านทั้ง 58 บัญชีใน `tb_Users` เก็บเป็น `sha256$` หมดแล้ว **รหัสของทุกคนไม่เปลี่ยน** สคริปต์เอาค่าเดิมมาเข้ารหัสทับที่เดิม และตรวจก่อนเขียนทุกแถวว่ารหัสเดิมยังผ่านการตรวจสอบด้วยค่าที่ hash แล้ว ถ้าแถวไหนไม่ผ่านจะหยุดทั้งรอบ ไม่ใช่เขียนไปครึ่งเดียวแล้วมีคนล็อกอินไม่ได้

รหัสตัวจริงอยู่ในไฟล์ `credentials_*.csv` บนเครื่องพัฒนาเท่านั้น ไฟล์นี้ถูก gitignore ไว้และไม่มีบนเซิร์ฟเวอร์

**ห้ามตั้ง `PASSWORD_PEPPER` บนเซิร์ฟเวอร์** ทุกบัญชี hash ด้วยค่าเริ่มต้นในโค้ด ตั้งค่าอื่นทับเมื่อไหร่ทุกคนล็อกอินไม่ได้ทันที

### 9.5 ระบบตรวจอัตโนมัติเมื่อส่งโค้ด

`.github/workflows/ci.yml` รันทุกครั้งที่ push ทุก branch และทุก PR เข้า main ฝั่ง backend รันชุดทดสอบบน Python 3.11 (รุ่นที่ Render ใช้) และ 3.13 (รุ่นบนเครื่องพัฒนา) โดยไม่ตั้ง `SESSION_SECRET` หรือ credential ใด ๆ ให้ ชุดทดสอบที่เริ่มพึ่งค่าจากเครื่องผู้พัฒนาจะพังตรงนี้ทันที แล้วตรวจต่อว่า API ประกอบร่างได้และมี endpoint ครบ 19 เส้นทางที่หน้าเว็บเรียก ฝั่ง frontend ตรวจชนิดข้อมูล lint และ build

### 9.6 ยังไม่ได้ตั้งค่าบนเซิร์ฟเวอร์จริง

ค่าตั้งค่าทั้งหมดยังอยู่บนเครื่องพัฒนา `render.yaml` กับขั้นตอนการนำขึ้นอยู่ใน `docs/deploy-render.md` แล้ว ตัวแปรที่ต้องตั้งบน Render คือ `SESSION_SECRET`, `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_OAUTH_REFRESH_TOKEN`, `DB_ROUTER_JSON`, `DIVISION_FOLDERS_JSON`, `CORS_ORIGINS` และค่า `AUTO_ARREST_*` ระบบจะไม่เริ่มทำงานถ้าไม่มี `SESSION_SECRET`

หน้า dashboard ระดับประเทศต้องมีตัวตั้งเวลายิง `POST /api/admin/aggregate-national` มารวมยอด ไม่งั้นหน้านั้นจะแสดงข้อมูลเก่าค้างไว้ ไม่ใช่ error Render Cron Jobs ต้องเสียเงิน แผนฟรีจึงใช้ตัวตั้งเวลาภายนอกแทน

### 9.7 LINE ยังไม่เคยทำงานจริง

`LINE_TOKEN` บนเครื่องพัฒนายังเป็นค่าตัวอย่าง การแจ้งเตือน LINE จึงยังไม่เคยส่งจริงเลยสักครั้ง ต้องเอา Channel Access Token จาก LINE Developers Console มาใส่ และตั้ง `lineGroupId` รายสถานีใน `STATION_SECRETS_JSON` ส่วนที่เหลือของระบบไม่ขึ้นกับเรื่องนี้ ส่ง LINE ไม่ผ่านจะบันทึกไว้ในบันทึกระบบเฉย ๆ รายงานที่บันทึกแล้วไม่กลายเป็นข้อผิดพลาด

## 10. วิธีตรวจสอบซ้ำ

```bash
cd python_backend

# ชุดทดสอบระดับหน่วยย่อย ไม่ต้องต่อเน็ต
python -m unittest discover -s tests -p "test_*.py"

# ตรวจการไหลของข้อมูลจริง เขียนแถวทดสอบแล้วลบออก
python scripts/verify_dataflow.py --cleanup

# ตรวจเฉพาะบางกองกำกับ และเก็บแถวไว้ดูด้วยตา
python scripts/verify_dataflow.py --divisions 5 --cleanup

# ตรวจว่าบัญชีระบบเข้าถึงไฟล์ครบทุกรายการ
python scripts/grant_system_access.py --verify

# รวมยอดระดับประเทศเองจากเครื่อง
python scripts/aggregate_national.py --days 7 --verbose

# ดูสถานะการเชื่อมต่อรายกองกำกับ
uvicorn app.main:app --reload --port 8000
# แล้วเรียก GET /api/health/database พร้อม header x-token
```

`verify_dataflow.py` อ่านรหัสผ่านทดสอบจากไฟล์ `credentials_*.csv` ล่าสุดใน `python_backend/` เพราะรหัสในชีตเข้ารหัสหมดแล้ว ระบุไฟล์เองได้ด้วย `--credentials`

## 11. ลำดับงานที่แนะนำต่อไป

1. นำขึ้น Render และ Vercel ตามขั้นตอนใน `docs/deploy-render.md` แล้วตั้ง `CORS_ORIGINS` ให้ตรงโดเมนที่ได้
2. ตั้งตัวตั้งเวลาภายนอกยิง `POST /api/admin/aggregate-national` ทุกชั่วโมง
3. ใส่ `LINE_TOKEN` ตัวจริงและ `lineGroupId` รายสถานี แล้วทดสอบการแจ้งเตือนจริง
4. ปิดการแชร์แบบเปิดของโฟลเดอร์ Drive (ขั้นที่ 2 ในหัวข้อ 9.1)
5. เพิ่มตัวยึดที่ขาดลงในแม่แบบบันทึกจับกุม ถ้าต้องการให้เอกสารพิมพ์ชื่อเจ้าหน้าที่ผู้รับผิดชอบและสถานที่ควบคุมตัว
