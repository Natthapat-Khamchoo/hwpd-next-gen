## 1. สรุปสำหรับผู้บริหาร

ก่อนเริ่มงาน ระบบรับข้อมูลจากฟอร์มได้แต่**ไม่ได้บันทึกลงที่ใดเลย** โค้ดฝั่งเซิร์ฟเวอร์เตรียมแถวข้อมูลไว้ครบแล้วโยนทิ้ง และหน้าเว็บแสดงข้อความว่าบันทึกสำเร็จทุกครั้งแม้เชื่อมต่อไม่ได้ ทำให้เจ้าหน้าที่เชื่อว่าส่งรายงานแล้วทั้งที่ข้อมูลหายไป

ตอนนี้รายงาน 3 ประเภทถูกบันทึกลงสเปรดชีตของกองกำกับการที่ถูกต้องจริง ทดสอบครบทั้ง 8 กก. ผ่าน 190 จาก 190 รายการ ระบบยืนยันตัวตนก่อนเขียนข้อมูลทุกครั้ง และเมื่อบันทึกไม่สำเร็จจะแจ้งเป็นข้อผิดพลาด ไม่แจ้งว่าสำเร็จอีกต่อไป

การล็อกอินตรวจกับแท็บ `tb_Users` ในชีตกลางแล้ว ไม่มีบัญชีหรือรหัสผ่านฝังอยู่ในโค้ดทั้งฝั่งเซิร์ฟเวอร์และหน้าเว็บอีกต่อไป และโหมดสาธิตต้องเปิดด้วยการตั้งค่าตอน build เท่านั้น

ฟอร์ม 11 จาก 14 ประเภทบันทึกลงชีตได้จริงแล้ว ที่เหลือ 3 รายการเป็นงานสรุปยอดและออกเอกสาร ซึ่งไม่ใช่การบันทึกแถวเดียว รายละเอียดอยู่ในหัวข้อ 8

## 3. งานด้านความปลอดภัย

**บังคับให้ `SESSION_SECRET` มาจาก environment**
ถอดค่าเริ่มต้นออกทั้งหมด ระบบไม่ยอมเริ่มทำงานถ้าไม่ได้ตั้งค่า และขึ้นบัญชีดำค่าเดิมสองตัวที่เคยอยู่ใน git ไว้ ถ้ามีคนนำกลับมาใช้ระบบจะปฏิเสธ

**ตรวจ session ทุกครั้งก่อนเขียนข้อมูล**
ทั้ง 3 ปลายทางตรวจ token จริง ไม่มี token หรือ token ปลอมได้ HTTP 401

**ตรวจสิทธิ์ระดับสถานี**
รหัสสถานีที่ส่งมาต้องอยู่ในขอบเขตที่ session นั้นมองเห็นได้ ตามกฎเดิมของระบบ (สถานีตรงกัน / ฝอ.กก. เห็นทั้งกองกำกับ / ส่วนกลางเห็นทั้งประเทศ) ส่งข้ามสถานีได้ HTTP 403

**ตรวจไฟล์แนบ**
จำกัด 10 ไฟล์ต่อรายงาน ไฟล์ละไม่เกิน 10 MB รับเฉพาะรูปภาพและ PDF ล้างชื่อไฟล์กัน path traversal

**ปิดช่องโหว่ formula injection**
เขียนข้อมูลด้วยโหมด `RAW` ทำให้ข้อความที่ขึ้นต้นด้วย `=` ไม่ถูกคิดเป็นสูตร

**หน้าเว็บจัดการ session หมดอายุ**
ถอด session ที่หมดอายุตั้งแต่โหลดหน้า และเมื่อเซิร์ฟเวอร์ตอบ 401 จะพากลับไปหน้าเข้าสู่ระบบพร้อมข้อความที่อ่านเข้าใจ

## 4. ชั้นบันทึกข้อมูล

**การยืนยันตัวตนกับ Google**
องค์กรบล็อกการสร้าง service account key (`iam.disableServiceAccountKeyCreation`) จึงใช้ OAuth ในนามบัญชี `marsocas.1998@gmail.com` แทน ระบบรองรับทั้งสองแบบ เลือก OAuth ก่อนถ้าตั้งค่าครบ

สถานะแอปใน Google Cloud ถูกเปลี่ยนเป็น **In production** แล้ว ทำให้ refresh token ไม่หมดอายุใน 7 วันแบบสถานะ Testing

**นิยามโครงสร้างตาราง** (`app/core/schema.py`)
หัวคอลัมน์คัดลอกจากชีตจริงที่ Apps Script สร้างไว้ ทุกตารางขึ้นต้นด้วย 9 คอลัมน์มาตรฐานตามพิมพ์เขียว มีชุดทดสอบตรวจว่าจำนวนช่องข้อมูลที่โค้ดสร้างตรงกับจำนวนคอลัมน์เสมอ ถ้าใครเพิ่มฟิลด์แล้วลืมแก้อีกฝั่ง ชุดทดสอบจะฟ้องทันที แทนที่จะปล่อยให้ข้อมูลลงผิดช่องเงียบ ๆ

**ตัวเขียนข้อมูล** (`app/services/sheets_service.py`)
สร้างแท็บพร้อมหัวคอลัมน์ให้อัตโนมัติถ้ายังไม่มี จำ handle ของแท็บไว้ใช้ซ้ำเพื่อประหยัดโควตา และรอแล้วลองใหม่เมื่อ Google ตอบว่าเกินโควตาชั่วคราว

**ลำดับการทำงานที่แก้ใหม่**
เดิมส่ง LINE ก่อนแล้วตอบสำเร็จโดยไม่สนใจว่าบันทึกได้หรือไม่ ตอนนี้ต้องเขียนชีตสำเร็จก่อน จึงจะส่ง LINE และตอบสำเร็จ ถ้าเขียนไม่ได้จะตอบ 503 (ยังไม่ตั้งค่า) หรือ 502 (Google ปฏิเสธ) พร้อมเหตุผลภาษาไทย ส่วนกรณีส่ง LINE ไม่ผ่านจะบันทึกไว้ในบันทึกระบบเฉย ๆ ไม่ทำให้รายงานที่บันทึกแล้วกลายเป็นข้อผิดพลาด

**เครื่องมือ**

## 7. บั๊กที่พบและแก้ไข

**เบอร์โทรสูญเสียเลข 0 นำหน้า**
`0812345678` ถูกบันทึกเป็น `812345678` เพราะส่งข้อมูลด้วยโหมดที่ให้ Google ตีความค่าใหม่แล้วอ่านเป็นตัวเลข แก้เป็นโหมด `RAW` ที่เก็บค่าตามที่ส่งไป

**ข้อมูลเดิมใน `DB_TEST_กก.1` ที่ Apps Script เขียนไว้มีปัญหาเดียวกัน** คอลัมน์เบอร์โทรทุกแถวขาดเลข 0 นำหน้า เป็นข้อบกพร่องที่มีมาก่อนหน้านี้ ควรพิจารณาแก้ข้อมูลเดิมและแก้ฝั่ง Apps Script ด้วยหากยังใช้งานคู่กัน

**เกินโควตาการอ่านของ Google**
ระบบอ่านโครงสร้างแท็บใหม่ทุกครั้งที่บันทึก ทำให้ชนเพดาน 60 ครั้งต่อนาที และรายงานของ กก.8 บันทึกไม่สำเร็จ แก้โดยจำ handle ของแท็บไว้ใช้ซ้ำ และรอแล้วลองใหม่เมื่อเจอโควตาเต็ม ทดสอบซ้ำแล้วผ่านครบทั้ง 8

**ข้อผิดพลาดของ Google หลุดออกมาเป็น HTTP 500**
แปลงให้เป็น 502 พร้อมข้อความภาษาไทยที่บอกวิธีแก้

**ชื่อฟิลด์ไฟล์แนบไม่ตรงกัน**
หน้าเว็บส่งชื่อ `files` แต่เซิร์ฟเวอร์รอรับ `fileDataArray` ไฟล์จึงถูกทิ้งโดยไม่มีการแจ้ง แก้ให้ตรงกัน และตั้งค่าให้ชื่อฟิลด์ที่ไม่รู้จักตอบ 422 แทนการทิ้งเงียบ

**สคริปต์ตั้งค่าฐานข้อมูลไม่อ่านไฟล์ `.env`**
แก้ให้ตัวเขียนข้อมูลโหลดค่าตั้งค่าเองไม่ว่าจะถูกเรียกจากทางใด

**รหัสรายงานซ้ำกันได้**
รหัสเดิมประกอบด้วยวันที่ระดับนาทีกับเลขสุ่ม 3 หลัก ตอนทดสอบส่งรายงานจาก 8 กก. พร้อมกัน มีสองใบได้รหัส `CHK-260726-2211-869` เหมือนกัน โอกาสชนราว 3% ต่อการส่งพร้อมกัน 8 ใบในนาทีเดียว

เรื่องนี้สำคัญเพราะการอนุมัติและการยกเลิกอ้างอิงด้วยรหัสรายงาน ถ้าชนกันในชีตเดียวกันจะไปดำเนินการกับใบผิด แก้เป็นวันที่ระดับวินาทีกับเลขสุ่ม 6 หลัก โอกาสชนเหลือประมาณ 0.003% (รูปแบบใหม่ `OP-260726-221145-482913`) ข้อมูลเดิมที่ใช้รูปแบบเก่าไม่ได้รับผลกระทบ

**ชุดทดสอบอ่านค่าจริงจากเครื่องผู้พัฒนา**
หลังจากตั้งค่าใช้งานจริง ชุดทดสอบเดิมเริ่มล้มเหลวเพราะไปหยิบค่าจริงมาใช้ แก้ให้แต่ละชุดกำหนดสภาพแวดล้อมของตัวเองให้ชัดเจน

**ป้ายหัวคอลัมน์ในชีตเดิมไม่ตรงกับข้อมูล** (ไม่ได้แก้ข้อมูลเดิม)
- `tb_DailyReport` ช่องที่ 14 เขียนว่า "รถวิทยุตรวจเขต" ซ้ำกับช่อง 13 ทั้งที่ข้อมูลที่บันทึกคือชื่อพลขับ
- `tb_Arrests` ช่องที่ 27 เขียนว่า `Structured_Items` แต่ข้อมูลที่บันทึกจริงคือขอบเขตหมาย ตรงตามที่ Apps Script ระบุไว้ในโค้ดของตัวเอง

แก้เฉพาะป้ายในไฟล์ที่สร้างใหม่ ไฟล์เดิมไม่ถูกแตะต้อง เนื่องจากทั้งระบบอ้างอิงข้อมูลด้วยตำแหน่งคอลัมน์ ไม่ใช่ชื่อ จึงไม่กระทบการทำงาน

## 8. ข้อจำกัดและงานที่เหลือ

### 8.1 เรื่องที่ควรจัดการก่อนใช้งานจริง

**การแชร์โฟลเดอร์ตั้งเป็น "ผู้ที่มีลิงก์แก้ไขได้"**
ทั้งโฟลเดอร์และทุกไฟล์ในนั้นเปิดให้ผู้ที่มีลิงก์แก้ไขและลบได้ และไฟล์ `MASTER_TEST_National` มีแท็บ `tb_Users` ที่เก็บชื่อผู้ใช้ รหัสผ่านแบบไม่เข้ารหัส ชื่อจริงและเบอร์โทรของเจ้าหน้าที่

หากจะปิด ให้แชร์ตรงให้บัญชีที่ต้องใช้เป็น Editor **ก่อน** แล้วจึงเปลี่ยนการแชร์เป็นจำกัด ทำสลับลำดับจะหลุดสิทธิ์ตัวเอง

ระบบไม่พึ่งการแชร์แบบเปิดแล้ว การอ่าน `tb_Users` เปลี่ยนไปใช้การยืนยันตัวตนชุดเดียวกับที่ใช้เขียนรายงาน จึงปิดการแชร์ได้โดยไม่กระทบการล็อกอิน

### 8.2 ฟอร์มที่ยังไม่มีปลายทางรับข้อมูล

**รองรับแล้ว 11 ประเภท**

| ฟอร์ม | ปลายทาง | ตาราง | รหัส |
|---|---|---|---|
| รายงานประจำวัน | `reports/daily` | `tb_DailyReport` | OP |
| ผลการปฏิบัติประจำวัน | `reports/daily-result` | `tb_DailyResult` | RST |
| ยอดเวรประจำสถานี | `reports/station-duty` | `tb_StationDuty` | STD |
| ภารกิจอื่น / จิตอาสา | `reports/other-duty` | `tb_OtherDuties` | OTH |
| ตั้งด่าน | `reports/checkpoint` | `tb_Checkpoints` | CHK |
| การจับกุม | `reports/arrest` | `tb_Arrests` | ARR |
| อุบัติเหตุ | `reports/accident` | `tb_Accidents` | ACC |
| แจ้งภารกิจ | `reports/mission` | `tb_Missions` | MIS |
| ถวายความปลอดภัย | `reports/royal-guard` | `tb_RoyalGuard` | RG |
| น้ำมัน / น้ำมันเครื่อง | `reports/fuel` | `tb_FuelOil` | FUEL |
| เอกสารสารบรรณ | `reports/document` | `tb_Documents` | DOC |

ลำดับคอลัมน์ของทุกตารางถอดมาจาก `appendRow` ใน `รหัส.js` โดยตรง และมีชุดทดสอบตรวจว่าจำนวนช่องข้อมูลตรงกับหัวคอลัมน์ทุกครั้งที่รัน

**ยังไม่รองรับ 3 รายการ** เพราะไม่ใช่การบันทึกแถวเดียวตรงไปตรงมา

- `daily-summary` สรุปยอดส่ง กก. เขียนลง `tb_HQ_Summary` ซึ่งเป็นตารางเดียวที่ไม่ได้ใช้ 9 คอลัมน์มาตรฐาน และต้องรวมยอดจากหลายแถวก่อน
- `mission-summary` สรุปผลภารกิจ ต้องอ่านภารกิจเดิมมาประมวลผลก่อน
- `auto-arrest` สร้างเอกสารจับกุมจากแม่แบบ Google Docs ไม่ได้เขียนลงตาราง

กดส่งจากหน้าเว็บทั้งสามรายการจะขึ้นข้อความว่าระบบยังไม่รองรับ ไม่ใช่แจ้งว่าสำเร็จ

### 8.3 เรื่องอื่น

**ข้อมูลสถานีครอบคลุมแค่ กก.1 และ กก.5**
สถานีของ กก.2, 3, 4, 6, 7, 8 ยังไม่มีชื่อจังหวัดและรายชื่อหน่วยบริการจริง ระบบใช้ชื่อที่สร้างขึ้นอัตโนมัติแทน การกำหนดเส้นทางฐานข้อมูลทำงานถูกต้องแล้ว แต่ชื่อที่แสดงและข้อความแจ้ง LINE จะยังไม่ใช่ของจริง ต้องได้ข้อมูลจากหน่วยมาเติม

**ยังไม่มีระบบตรวจอัตโนมัติเมื่อส่งโค้ด**
ไม่มีการรันชุดทดสอบอัตโนมัติ ควรเพิ่มเพื่อไม่ให้โค้ดที่ทำให้ชุดทดสอบล้มเหลวถูกส่งขึ้นไป

**ยังไม่ได้ตั้งค่าบนเซิร์ฟเวอร์จริง**
ค่าตั้งค่าทั้งหมดอยู่บนเครื่องพัฒนา หากจะนำขึ้น Render ต้องตั้ง `SESSION_SECRET`, `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_OAUTH_REFRESH_TOKEN`, `DB_ROUTER_JSON` และ `DIVISION_FOLDERS_JSON` ในหน้า Environment ระบบจะไม่เริ่มทำงานถ้าไม่มี `SESSION_SECRET`
