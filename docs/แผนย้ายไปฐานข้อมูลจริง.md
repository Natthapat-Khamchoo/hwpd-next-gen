# แผนย้ายจาก Google Sheets ไปฐานข้อมูลจริง

เอกสารนี้เป็นแผนพัฒนาต่อ ไม่ใช่คู่มือใช้งาน ทุกตัวเลขในนี้วัดจากระบบที่ใช้งานอยู่จริง
ณ วันที่ 1 สิงหาคม 2569

## สรุปสั้น

ระบบทำงานได้ดีบน Google Sheets แต่ชนเพดานที่แก้ด้วยโค้ดไม่ได้แล้วสามเรื่อง —
โควตาการอ่าน เพดานจำนวนแถว และการไม่มี transaction

**ข้อมูลทั้งระบบตอนนี้มีราว 561 แถว** ฐานข้อมูลฟรีตัวไหนก็รับได้สบาย งานนี้จึงไม่ใช่
เรื่องปริมาณข้อมูล แต่เป็นเรื่องความถูกต้องและการรองรับคนใช้พร้อมกัน

---

## 1. ทำไมต้องย้าย

ทุกข้อต่อไปนี้เกิดขึ้นจริงระหว่างพัฒนา ไม่ใช่ปัญหาที่คาดเดาเอาไว้ล่วงหน้า

| ปัญหา | สิ่งที่เกิดขึ้นจริง | แก้ด้วยโค้ดได้ไหม |
|---|---|---|
| โควตาอ่าน 60 ครั้ง/นาที ต่อ 1 บัญชี และทั้งระบบใช้บัญชีเดียว | เจอ 429 ตอนออกรายงาน | บรรเทาได้ด้วยแคช แต่เพดานยังอยู่ |
| ชีตมีเพดานจำนวนแถว | `tb_National_Summary` เต็ม 1,023 แถว การรวมยอด **หาย 6 กก. แบบเงียบ ๆ** | ขยายชีตได้ แต่โตไปเรื่อย ๆ |
| ไม่มี transaction | รายงานประจำวัน 5 แท็บ = เขียน 5 ครั้งแยกกัน พังกลางคันได้ | ไม่ได้ |
| ไม่มีการล็อกแถว | อ่านเลขแถวมาแล้วเขียนทับ ถ้ามีคนลบแถวคั่นกลางจะเขียนผิดแถว | เลี่ยงได้แต่เปราะ |
| อ้างคอลัมน์ด้วยตำแหน่ง | หัวตารางในชีตไม่ตรงกับข้อมูลอยู่แล้วบางตัว (ดู `schema.py`) | ไม่ได้ |
| ถามข้ามหน่วยต้องเปิดทีละไฟล์ | รายงานตามหมวด = เปิด 2 ตาราง x 8 กก. = 16 ครั้ง | บรรเทาด้วยแคชแล้ว |

## 2. ของที่มีอยู่แล้วและช่วยให้ย้ายง่ายกว่าที่คิด

**`app/core/schema.py` นิยามครบแล้ว 13 ตาราง 251 คอลัมน์** — DDL ของฐานข้อมูลใหม่
แทบเขียนเสร็จอยู่แล้ว ไม่ต้องมานั่งไล่ดูชีตทีละแท็บ

**ทุกตารางขึ้นต้นด้วย 9 คอลัมน์ระบบเหมือนกันหมด** (`Sys_RecordID`, `Sys_Timestamp`,
`Sys_LastUpdate`, `Sys_ActionBy`, `Sys_Status`, `Sys_IsActive`, `Data_ActualDate`,
`Data_StationID`, `Data_UnitID`) เป็นฐานร่วมที่ยกไปเป็นตารางแม่ได้ทันที

**การแตะ Google กระจุกอยู่ที่เดียว** — นอก `sheets_service` มีจุดที่เรียกตรงแค่ 19 จุด
ใน 9 ไฟล์ ไม่ได้กระจายทั่วโค้ด

**`Sys_RecordID` ไม่ซ้ำอยู่แล้ว** ใช้เป็น primary key ได้เลย ไม่ต้องสร้างคีย์ใหม่

**ชุดทดสอบ 263 รายการ stub ที่ `read_table`** ซึ่งอยู่ตรงรอยต่อพอดี ย้ายรอยต่อแล้ว
เทสเดิมยังใช้ตรวจได้ว่าพฤติกรรมไม่เปลี่ยน

## 3. เลือกฐานข้อมูล

ข้อบังคับตอนนี้คือ **ต้องไม่มีค่าใช้จ่าย** เพราะยังเป็นตัวสาธิต

**PostgreSQL** เพราะรองรับ JSON (ตารางมีคอลัมน์ JSON อยู่แล้ว เช่น ของกลาง สถิติในแคช)
มีเครื่องมือครบ และย้ายไปเสียเงินทีหลังได้โดยไม่ต้องเปลี่ยนโค้ด

เกณฑ์เลือกผู้ให้บริการ — **ต้องเช็คเงื่อนไขล่าสุดก่อนตัดสินใจ เพราะแผนฟรีเปลี่ยนบ่อย**

| เกณฑ์ | ทำไมสำคัญกับงานนี้ |
|---|---|
| ไม่มีวันหมดอายุ | บางเจ้าให้ฟรีแค่ 30–90 วันแล้วลบฐานข้อมูลทิ้ง ใช้กับงานที่ต้องสาธิตต่อเนื่องไม่ได้ |
| ตื่นเร็วหลังพัก | แผนฟรีมักพักเมื่อไม่มีคนใช้ ถ้าตื่นช้าจะซ้ำปัญหาเดิมกับ Render |
| ภูมิภาคใกล้ไทย | ตอนนี้เสีย 0.35 วินาทีต่อคำขอไปกับระยะทางแล้ว อย่าเพิ่มอีกชั้น |
| สำรองข้อมูลอัตโนมัติ | ข้อมูลราชการ ต้องกู้คืนได้ |

พื้นที่ไม่ใช่ประเด็น — 561 แถวใช้ไม่ถึง 1 MB แผนฟรีทุกเจ้าเหลือเฟือ

## 4. ตัดสินใจเรื่องโครงสร้างก่อนเริ่ม

### 4.1 ยกมาทั้งดุ้นก่อน อย่าเพิ่งจัดระเบียบ

ทำตารางใน Postgres ให้เหมือนชีต 1:1 ก่อน แล้วค่อยปรับโครงทีหลัง

เหตุผล: ถ้าย้ายและจัดโครงใหม่พร้อมกัน เวลาตัวเลขไม่ตรงจะแยกไม่ออกว่าเพราะย้ายผิด
หรือเพราะโครงใหม่ ทำทีละอย่างจะตรวจได้ว่ายอดต้องเท่าเดิมเป๊ะ

### 4.2 รวม 8 ฐานข้อมูล กก. เป็นฐานเดียว

ตอนนี้แยกเป็น 8 สเปรดชีตเพราะชีตมีเพดาน ฐานข้อมูลจริงไม่มีข้อจำกัดนั้น

เพิ่มคอลัมน์ `division` แล้วรวมเป็นตารางเดียวต่อชนิดรายงาน — การถามข้ามหน่วยจาก
16 การอ่าน เหลือคำสั่งเดียว

### 4.3 ชื่อคอลัมน์ภาษาไทย — ต้องตัดสินใจตั้งแต่ต้น

ตอนนี้คอลัมน์ชื่อไทยล้วน เช่น `ยอด ว.20`, `จำนวนผู้ต้องหา`

**แนะนำให้เปลี่ยนเป็นอังกฤษใน DB แล้วแปลงชื่อที่ชั้นแอป** เพราะชื่อไทยใน SQL ต้องใส่
เครื่องหมายคำพูดทุกครั้ง (`"ยอด ว.20"`) ซึ่งลำบากทั้งตอนเขียน query ตอนใช้เครื่องมือ
และตอน debug ส่วนชื่อไทยที่ผู้ใช้เห็นย้ายไปอยู่ในชั้นแปลง ซึ่งมี `schema.py` รองรับอยู่แล้ว

### 4.4 เลิกใช้เลขแถว เปลี่ยนไปใช้ `Sys_RecordID`

โค้ดตอนนี้อ่านเลขแถวมาแล้วเขียนกลับที่แถวนั้น (`_row`) ซึ่งเป็นแนวคิดของสเปรดชีต
ฐานข้อมูลจริงใช้ `WHERE Sys_RecordID = ?` แทน ปลอดภัยกว่าและไม่ต้องกลัวแถวเลื่อน

## 5. ลำดับการทำงาน

### ระยะ 0 — ทำรอยต่อให้ชัด (ยังไม่แตะฐานข้อมูล)

สร้างชั้นกลางสำหรับเข้าถึงข้อมูล แล้วย้าย 19 จุดที่เรียก Google ตรง ๆ มาผ่านชั้นนี้

จบระยะนี้แล้วโค้ดส่วนที่เหลือจะไม่รู้จัก Google Sheets อีกเลย และ**ระบบยังทำงาน
เหมือนเดิมทุกอย่าง** — ทำได้โดยไม่ต้องหยุดให้บริการ

*ผลลัพธ์ที่วัดได้: `grep` หาคำว่า gspread นอกชั้นนี้ต้องไม่เจอ*

### ระยะ 1 — สร้างฐานข้อมูลและตาราง

สร้าง DDL จาก `schema.py` โดยเพิ่มของที่ชีตให้ไม่ได้

- ชนิดข้อมูลจริง — วันที่เป็น `date` จำนวนเป็น `integer` ไม่ใช่ข้อความทั้งหมด
- `Sys_RecordID` เป็น primary key
- ดัชนีที่ `(division, Data_StationID, Data_ActualDate, Sys_Status)` ซึ่งเป็นเงื่อนไข
  ที่แทบทุกหน้าถามหา

### ระยะ 2 — เขียนสองที่ อ่านที่เดิม

เขียนลงทั้งชีตและฐานข้อมูล แต่ยังอ่านจากชีตอย่างเดียว

เขียนสคริปต์เทียบยอดรันทุกวัน — จำนวนแถวและผลรวมของทุกตารางต้องตรงกัน
ปล่อยไว้จนกว่าจะตรงติดกันหลายวัน

**ระยะนี้ห้ามข้าม** ถ้าฐานข้อมูลใหม่มีปัญหาก็แค่หยุดเขียน ไม่กระทบผู้ใช้เลยสักคน

### ระยะ 3 — ย้ายการอ่านทีละหน้า

ไล่ทีละ endpoint ไม่ใช่สลับทีเดียวทั้งระบบ เรียงจากเสี่ยงน้อยไปมาก

1. รายงานและการรวมยอด (อ่านอย่างเดียว ผิดแล้วออกใหม่ได้)
2. หน้า dashboard ระดับ บก. และ กก.
3. คิวรออนุมัติของสถานี (คนใช้เยอะสุด ย้ายท้ายสุด)

แต่ละตัวเทียบผลกับของเดิมก่อนแล้วค่อยสลับ

### ระยะ 4 — เลิกใช้ชีตเป็นฐานข้อมูล

หยุดเขียนลงชีต แต่**เก็บชีตไว้เป็นปลายทางส่งออก** เพราะเจ้าหน้าที่คุ้นเคยกับการเปิดดู
ในชีตอยู่แล้ว เปลี่ยนสถานะจาก "ฐานข้อมูล" เป็น "รายงานที่ระบบสร้างให้"

## 6. สิ่งที่ดีขึ้นทันทีเมื่อย้ายเสร็จ

| เรื่อง | ตอนนี้ | หลังย้าย |
|---|---|---|
| ถามข้ามทั้ง 8 กก. | เปิด 16 ครั้ง | คำสั่งเดียว |
| รวมยอดระดับประเทศ | เป็นนาที ต้องทำเบื้องหลัง | เป็นมิลลิวินาที ทำสด |
| แคชรายงาน | ต้องมี เพราะโควตา | ไม่จำเป็นแล้ว |
| เพดานจำนวนแถว | มี และเคยทำข้อมูลหายมาแล้ว | ไม่มี |
| รายงานประจำวัน 5 แท็บ | เขียน 5 ครั้งแยกกัน | ครั้งเดียวแบบ atomic |
| ค้นหาเชิงลึก | สแกนทั้งตารางในแอป | ให้ฐานข้อมูลค้นด้วยดัชนี |
| ผู้ใช้พร้อมกัน | ~10 คน/นาที | หลักร้อย |

## 7. ความเสี่ยงที่ต้องจัดการ

**มีใครแก้ชีตด้วยมือบ้างหรือเปล่า** — ต้องตอบให้ได้ก่อนถึงระยะ 4 ถ้ามีคนเปิดชีตแก้
ตัวเลขเองอยู่ การหยุดเขียนลงชีตจะตัดวิธีทำงานของเขาโดยไม่มีใครรู้ตัว

**แผนฟรีของฐานข้อมูลก็พักเหมือน Render** — ถ้าทั้งเว็บและฐานข้อมูลพักพร้อมกัน
คนแรกของวันจะรอนานกว่าเดิม ควรวัดจริงในระยะ 2

**ข้อมูลราชการอยู่นอก Google แล้ว** — ต้องตอบเรื่องการสำรองข้อมูลและสิทธิ์เข้าถึง
ให้ได้ก่อนเปลี่ยน ไม่ใช่หลังเปลี่ยน

**อย่าเพิ่งเลิกใช้ Drive** — ไฟล์แนบและเอกสารจับกุมยังอยู่บน Google Drive และไม่มี
เหตุผลต้องย้าย แผนนี้พูดถึงเฉพาะตารางข้อมูล

## 8. สิ่งที่ควรทำก่อนเริ่มระยะ 0

เรื่องเหล่านี้ค้างอยู่และควรจบก่อน ไม่งั้นจะลากปัญหาเดิมข้ามไปฐานข้อมูลใหม่ด้วย

1. **ปิดการแชร์ Drive แบบสาธารณะ** — ตอนนี้ไฟล์ 20 รายการยังเปิดให้ทุกคนที่มีลิงก์
   แก้ไขได้ รวมถึงแท็บที่เก็บชื่อจริงและเบอร์โทรเจ้าหน้าที่
2. **เติมชื่อจริงแทน `(รอระบุชื่อ)` 43 บัญชี**
3. **ให้ฝ่ายกฎหมายตรวจถ้อยคำข้อหาที่เพิ่มใหม่ 18 รายการ**
4. **ล้างข้อมูลทดสอบออก** ไม่งั้นจะถูกย้ายไปฐานข้อมูลใหม่ปนกับของจริง
